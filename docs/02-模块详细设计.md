## M1 配置模块 `config/`

**职责**：集中管理所有配置，支持多环境、环境变量覆盖、版本化。

```python
# 用 pydantic-settings，环境变量前缀 RAGFORGE_
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="RAGFORGE_", env_file=".env")

    # LLM
    llm_provider: str = "openai"
    llm_model: str = "deepseek-chat"
    llm_api_key: SecretStr
    llm_fallback_chain: list[str] = ["openai", "doubao"]

    # 检索
    retrieval_top_k: int = 50  # 召回条数
    rerank_top_n: int = 8  # 重排后条数
    rrf_k: int = 60  # RRF 参数

    # 缓存
    semantic_cache_enabled: bool = True
    semantic_cache_threshold: float = 0.92

    # 观测
    otel_endpoint: str | None = None
```

**工程细节**：
- 敏感信息用 `SecretStr`，日志中自动脱敏。
- 配置分层：`default` → `dev` → `prod`，通过 `RAGFORGE_ENV` 切换。
- 配置变更走评审（config-as-code），Prompt 版本与代码版本解耦。

## M2 LLM Provider `core/llm`

**职责**：统一 LLM 调用接口，屏蔽 provider 差异，支持流式、结构化输出、fallback。

```python
class BaseLLM(ABC):
    @abstractmethod
    async def complete(
        self, messages: list[Message], temperature: float = 0.0, max_tokens: int | None = None
    ) -> LLMResult: ...

    @abstractmethod
    async def stream(self, messages: list[Message], **kw) -> AsyncIterator[Token]: ...

    @abstractmethod
    async def complete_structured(self, messages: list[Message], schema: dict) -> dict: ...
```

**关键逻辑**：
1. **Fallback 链**：按 `llm_fallback_chain` 顺序调用，捕获 `TimeoutError/ConnectionError/5xx` 自动降级，每跳记录耗时与失败原因（写进 trace）。
2. **重试**：指数退避 + 抖动，仅对幂等错误重试。
3. **熔断**：单 provider 连续失败 ≥ 5 次打开熔断，60s 后半开探测。
4. **结构化输出**：用 JSON Schema 约束，失败时自动修复（补全/重试），返回 dict。
5. **Token 统计**：每次调用返回 `prompt_tokens / completion_tokens / cost`，用于成本核算。

## M3 Embedding `core/embeddings`

```python
class EmbeddingProvider(ABC):
    def embed(self, texts: list[str], batch_size: int = 32) -> list[list[float]]: ...
    def embed_query(self, text: str) -> list[float]: ...  # 指令前缀区分
```

**关键逻辑**：
- **批量**：入库批量向量化，降本提速。
- **query/doc 区分**：BGE 等模型 query 与 doc 需不同指令前缀（`query:` / `passage:`），封装在 provider 内。
- **维度校验**：入库与查询维度不一致时立刻抛错，避免静默产生垃圾向量。
- **缓存**：doc embedding 持久化到 Redis/磁盘，文档重复入库时复用。

## M4 文档解析 `ingestion/parsers`

**职责**：把各种格式文档解析为带结构的文本。

```
Parser(ABC).parse(file) -> ParsedDocument
    ├── PDFParser    # MinerU：文本 + 版面 + 表格 + 公式 + OCR
    ├── WordParser   # python-docx：标题层级 + 段落 + 表格
    ├── MarkdownParser  # 标题树 + 代码块 + 列表
    └── WebParser    # HTML → 正文抽取（去导航/广告）
```

**数据结构**：
```python
@dataclass
class ParsedDocument:
    doc_id: str
    title: str
    sections: list[Section]  # 层级结构
    tables: list[Table]  # 表格结构化
    metadata: dict  # 来源/作者/时间/权限
```

**工程细节**：解析是重任务 → 全部走 Celery 异步；失败进入重试/死信；支持"增量解析"（只解析变更文档）。

## M5 分块 `ingestion/chunking`

**职责**：把文档切成语义完整、可检索、可还原上下文的 chunk。这是 RAG 质量的最大变量之一。

```python
class Chunker(ABC):
    def split(self, doc: ParsedDocument) -> list[Chunk]: ...


@dataclass
class Chunk:
    chunk_id: str
    doc_id: str
    text: str
    parent_id: str | None  # 父块
    heading_path: list[str]  # 标题路径 ["产品文档","计费","价格"]
    page: int | None
    metadata: dict
```

**三种策略（可配置，可 A/B）**：

1. **结构感知分块（默认）**：按文档标题树切分，每个 section 一个 chunk，保留 `heading_path`。适合手册/制度类文档。
2. **语义分块**：基于 embedding 相邻句相似度找"语义边界"切分。适合无结构长文。
3. **父子分块（Parent-Child）**：
   - **child（小块，~200 tokens）**：用于检索，精度高。
   - **parent（大块，~800 tokens）**：生成时还原完整上下文。
   - 检索命中 child → 用 `parent_id` 取回 parent → 送入 LLM。

**工程细节**：
- 重叠窗口 `overlap` 避免语义被切断。
- 入库前用 `chunk_id = hash(doc_id + heading_path + 序号)` 保证幂等。
- 分块参数（大小/重叠/策略）是**可评估的超参**，通过评测选最优。

## M6 向量库 / 文档库 `core/vector_store`

```python
class VectorStore(ABC):
    def add(self, chunks: list[Chunk]) -> None: ...
    def search(
        self, embedding: list[float], top_k: int, filters: dict | None = None
    ) -> list[SearchHit]: ...
    def search_hybrid(self, embedding, text, top_k, filters) -> list[SearchHit]: ...


@dataclass
class SearchHit:
    chunk_id: str
    score: float
    chunk: Chunk | None = None
```

**实现**：
- `MilvusVectorStore`：dense 向量（HNSW 索引）+ 标量过滤。
- `ElasticsearchStore`：BM25 全文索引（sparse 召回）。
- 统一通过 `Retriever` 组合两者。

**工程细节**：
- 向量维度、索引类型、`ef` 参数在配置中声明，启动时校验 schema。
- 写入失败用 `upsert` 幂等语义。
- 查询加 `filters`（如 `doc_id`、`权限域`）实现**文档级权限隔离**（企业场景刚需）。

## M7 查询理解 `query/`

**职责**：把用户原始问题转化为更适合检索的形式。这是"普通 RAG 与进阶 RAG"的分水岭。

**管线（可配置启停）**：

```
raw_query
  → [意图识别] 分类：问答/检索/闲聊/多跳/拒绝
  → [查询改写] 消除指代、补全上下文（结合多轮对话历史）
  → [多查询扩展] 从不同角度生成 3~5 个相关查询
  → [HyDE] 生成"假设性答案文档"，用假设答案去检索
```

```python
@dataclass
class QueryUnderstanding:
    raw_query: str
    intent: str
    rewritten_query: str
    expanded_queries: list[str]  # 多查询
    hyde_doc: str | None  # 假设文档
```

**关键逻辑**：
- 多轮对话需要**指代消解**（"它呢？"→"上一轮提到的 X"），改写 prompt 里带入历史。
- 多查询 + 原始查询**并行召回**，结果融合，提升召回率。
- 所有子查询的 prompt 见 `03-Prompt提示词库.md`。

## M8 检索 `retrieval/`

**职责**：多路召回 → 融合 → 重排。

```
检索器 Retriever
   ├── DenseRetriever  (Milvus 向量)
   ├── SparseRetriever (ES BM25)
   └── HybridRetriever (组合以上 + RRF)
```

**RRF 融合公式**（面试可写）：
```
score(d) = Σ 1 / (k + rank_i(d))，k 默认 60
```

**重排**：Cross-Encoder 对 (query, chunk) 打分精排，取 top-n。延迟敏感时可先粗排 top-k(50) 再精排 top-n(8)，**两级漏斗**降本提效。

**工程细节**：
- 召回、重排全程记录：每路 top-k、分数、耗时 → trace。
- 检索结果去重（同 chunk 多路命中取最高分）。
- 支持**元数据过滤**（时间范围、文档类型、权限）。

## M9 自评纠错 Self-RAG / CRAG `retrieval/self_rag`

**职责**：生成前评估检索质量，不足则纠错，而不是硬答。

```
检索结果 → [相关性自评] 对每条 chunk 打分(相关/不相关)
   ├── 全部相关 → 直接生成
   ├── 部分相关 → 用"改写后的查询"重试检索(CRAG)
   └── 全部不相关 → 触发外部工具(可选)/明确告知"资料不足"（反幻觉）
```

```python
@dataclass
class SelfRagAssessment:
    verdict: str  # "sufficient" | "retry" | "insufficient"
    relevance: list[bool]  # 每条 chunk 是否相关
    refined_query: str | None
```

**工程细节**：自评用 LLM 批量判断（一个 prompt 评全部 chunk），判断结果进 trace；自评本身也纳入评估（防止自评模型误判）。

## M10 生成 `generation/`

**职责**：上下文装配 → 构造 prompt → 流式生成 → 引用溯源 → 输出。

**上下文装配（Context Assembly）—— 面试亮点**：
1. **Token 预算**：`max_context_tokens` 减去 system prompt + 预留输出，剩下的分给 chunk。
2. **排序截断**：按重排分数从高到低填充，直到预算用尽。
3. **去重**：相似 chunk（embedding 相似度 > 阈值）只保留一条。
4. **父子块还原**：命中 child 时取回 parent 补全上下文。
5. **引用编号**：每个 chunk 分配 `[1][2][3]`，答案中引用对应编号，返回 `chunk_id + 页码`。

```python
@dataclass
class GenerationResult:
    answer: str
    citations: list[Citation]  # [{"chunk_id","page","text","score"}]
    prompt_tokens: int
    completion_tokens: int
    latency_ms: float
    cost: float
```

**流式**：SSE 逐 token 推送，首字延迟（TTFT）作为核心指标。

## M11 缓存 `cache/`

**职责**：降低延迟与成本。

1. **精确缓存**：`key = hash(query)`，命中直接返回。
2. **语义缓存**：`key = embedding(query)`，在 Redis 中按相似度（阈值 0.92）查找最近缓存。

**关键逻辑**：
- 缓存值存 `(answer, citations, source_query)`，命中时返回并标记"缓存命中"。
- 缓存命中不进 trace 的 LLM 段，单独记 `cache_hit = true`。
- 支持 TTL 与主动失效（文档更新时按 doc_id 清缓存）。

## M12 Agentic RAG `agent/`

**职责**：处理需要多跳推理/工具调用的复杂问题。

```
复杂问题 → [规划] 拆解为子问题 → [执行] 逐个子问题检索/生成/工具调用
   → [反思] 校验答案一致性 → 不足则修正/重试 → 汇总最终答案
```

**工具集（Tools）**：`检索工具`、`计算器`、`查表(结构化数据)`、`联网搜索(可选)`。

**技术选型**：LangGraph 或自研状态机。核心是 **ReAct / Reflection 模式**。
> 简历表述：基于 ReAct + Reflection 实现多跳 Agentic RAG，复杂问答准确率提升 XX%。

## M14 可观测 `observability/`

**职责**：三件套 —— **Trace / Metrics / Log**。

1. **Trace（OpenTelemetry + Langfuse）**：一次 query 的 span 树：`query → rewrite → retrieve(dense/sparse) → rerank → self_rag → generate`，每个 span 记录耗时/token/分数。
2. **Metrics（Prometheus）**：延迟分位(P50/95/99)、召回命中、缓存命中率、成本、QPS、错误率。
3. **Log（structlog）**：JSON 结构化，统一带 `trace_id / request_id`，方便关联检索。

```python
# 每个 span 结构（示例）
Span("retrieve") { query, top_k, latency_ms, hits: [...], scores: [...] }
Span("generate") { prompt_tokens, completion_tokens, cost, latency_ms }
```

## M15 护栏 `guardrails/`

**职责**：安全与质量兜底。

1. **输入护栏**：敏感/违规/越权内容检测，命中则拒绝并返回友好提示。
2. **输出护栏**：生成内容合规检查、幻觉检测（答案是否可被引用支撑）。
3. **拒答策略**：资料不足时明确说"我不知道"，而不是编造。

## M16 API `api/`

**职责**：对外服务接口。

```python
POST / v1 / chat  # 非流式问答
POST / v1 / chat / stream  # SSE 流式问答
POST / v1 / documents  # 上传文档（触发异步入库）
GET / v1 / documents / {id}  # 入库状态查询
GET / v1 / health  # 健康检查（含下游依赖探活）
GET / v1 / metrics  # Prometheus 指标
```

**统一响应结构**：
```json
{ "code": 0, "data": {...}, "trace_id": "...", "cost": {"latency_ms": 123, "tokens": 456} }
```

**工程细节**：全局异常处理器 → 统一错误码；请求体 Pydantic 校验；限流（令牌桶）；`X-Request-ID` 透传。
