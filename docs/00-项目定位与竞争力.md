> 本文档回答三个问题：**为什么做**、**做成什么样才够格写进简历**、**和网上千篇一律的 RAG Demo 差在哪**。
> 阅读顺序：本文件 → `01-系统架构设计` → `02-模块详细设计` → 其余按需。

---

## 1. 项目一句话定位

> **RAGForge —— 一个工程化、可评估、可观测、可灰度发布的企业级检索增强生成（RAG）平台。**

它不是"把 PDF 切成 chunk 塞进向量库然后问一句答一句"的玩具，而是一套具备以下工业级能力的完整系统：

- **可评估**：任何一次改动（换 embedding、换分块策略、换 prompt）都能被指标量化，而不是"感觉变好了"。
- **可观测**：一次问答从查询理解 → 检索 → 重排 → 生成的每一步都有 trace、耗时、成本、召回列表。
- **可灰度**：新版本通过 A/B 实验小流量验证后再全量，支持一键回滚。
- **可降级**：LLM 挂了有 fallback 链，向量库抖了有缓存兜底，绝不整链路雪崩。

## 2. 目标岗位与项目匹配度

| 岗位 JD 常见要求 | 本项目如何命中 |
| --- | --- |
| 熟悉 RAG / 检索增强 / LLM 应用 | 自研完整 RAG 管线：混合检索、重排、查询改写、Self-RAG、Agentic RAG |
| 熟悉向量数据库 | 抽象向量库接口，接入 Milvus + Elasticsearch，实现混合检索 |
| 有大模型评测经验 | 自建黄金集 + RAGAS + 自研指标（recall@k、faithfulness 等）离线/在线闭环 |
| 工程能力强、有系统设计思维 | 分层架构、依赖注入、接口抽象、12-factor、CI/CD、k8s 部署 |
| 关注性能与成本 | 语义缓存、Token 预算、延迟 SLO、P50/P95/P99 度量、成本/查询 |
| 有 Agent 开发经验 | Agentic RAG：多跳推理、工具调用、反思（Reflection）、CRAG 纠错 |

**结论**：这个项目不是"另一个 RAG Demo"，而是把一个 RAG 系统当**线上生产系统**来设计和交付，这正是 Agent/LLM 应用工程师岗位区分度最高的地方。

## 3. 技术亮点清单（面试时的"弹药"）

按难度/区分度从高到低排列，面试时优先讲前 6 条。

### 亮点 1：多路召回 + 融合重排的混合检索
- **Dense 检索**（向量相似度）+ **Sparse 检索**（BM25 关键词）+ 可选 **知识图谱/结构化字段过滤**。
- 多路结果用 **RRF（Reciprocal Rank Fusion）** 融合，再交给 **重排模型（Cross-Encoder）** 精排。
- 解决纯向量检索对"精确实体、编号、缩写、低频词"召回差的痛点。

### 亮点 2：查询理解管线（Query Understanding）
- 输入一个模糊问题，先经过**意图识别 → 查询改写 → 多查询扩展 → HyDE（假设文档）** 再检索。
- 把"用户想表达什么"与"系统应该检索什么"解耦，显著提升召回率。

### 亮点 3：Self-RAG / CRAG（检索自评与纠错）
- 生成前先用 LLM 对检索结果做**相关性自评**，判断"检索是否足够 / 是否需要改写重试 / 是否走外部工具"。
- 实现 **Corrective RAG（CRAG）**：检索质量不达标时自动纠错重试，而非硬着头皮生成。

### 亮点 4：结构感知分块 + 父子分块（Parent-Child Chunking）
- 分块不是一刀切，而是基于**文档标题树/版面结构**切分，保留层级关系。
- 检索用"小块"保证精度，生成用"父块/邻居块"还原上下文，兼顾召回与生成质量。

### 亮点 5：语义缓存（Semantic Cache）
- 用 embedding 相似度做缓存键，相似问题直接命中缓存，跳过 LLM 调用。
- 落地为**成本/延迟优化**：命中率、成本节省、延迟下降都是可量化的简历数字。

### 亮点 6：上下文工程与可溯源引用（Citation）
- 上下文窗口**预算管理**：按相关性分数、Token 预算、去重策略动态装配 context。
- 答案**强制带引用**（返回 chunk 来源、页码、链接），降低幻觉、可审计。

### 亮点 7：全链路可观测性
- OpenTelemetry 全链路 trace：一次 query 的每一步（改写/检索/重排/生成）耗时与 token 全记录。
- Prometheus 指标 + Grafana 面板：延迟分位、召回命中、缓存命中率、成本。

### 亮点 8：Agentic RAG
- 复杂问题拆解为**多跳子问题**，Agent 通过工具（检索、计算、查表）逐步求解，最后反思校验。

## 4. 与"普通 RAG Demo"的差距对照表

| 维度 | 普通 Demo | 本项目（RAGForge） |
| --- | --- | --- |
| 检索 | 单一向量 top-k | 多路召回 + RRF 融合 + 重排 |
| 查询 | 原样检索 | 意图识别 + 改写 + 多查询 + HyDE |
| 分块 | 固定 500 字符切 | 结构感知 + 语义 + 父子分块 |
| 生成 | 一次性拼接 | Token 预算、引用溯源、Self-RAG 自评 |
| 缓存 | 无 | 精确缓存 + 语义缓存 |
| 评估 | 人工"看着还行" | 黄金集 + RAGAS + 自研指标 + A/B |
| 可观测 | print 日志 | trace + metrics + 结构化日志 |
| 可靠性 | 挂了就挂了 | fallback 链、熔断、重试、降级 |
| 部署 | 本地脚本 | Docker + k8s + CI/CD + 灰度 |
| 配置 | 硬编码 | pydantic-settings 分层配置 + 版本化 |
| 测试 | 无 | 单测 + 集成 + e2e + Mock LLM |

## 5. 核心量化目标（简历要写的数字）

在面试/简历中，你需要能给出**真实测量**的数值。项目验收时按以下目标跑通：

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| 检索 Recall@5 | ≥ 0.90 | 黄金集上命中率 |
| 检索 MRR | ≥ 0.80 | 排序质量 |
| 答案 Faithfulness | ≥ 0.90 | RAGAS，答案忠于上下文 |
| 答案 Answer Relevance | ≥ 0.85 | RAGAS |
| 端到端延迟 P95 | ≤ 3s | 不含流式首字更优 |
| 语义缓存命中率 | ≥ 30% | 相似问题直接命中 |
| LLM 成本下降 | ≥ 30% | 相对无缓存基线 |
| 单元测试覆盖率 | ≥ 85% | 核心模块 |

> ⚠️ 这些数字必须**跑出来**，不能编。项目里已内置评测脚本，跑一遍就有数。面试官大概率会追问"这个数字怎么测的"。

## 6. 技术栈总览（一屏看懂）

| 层 | 技术选型 | 备注 |
| --- | --- | --- |
| 语言/环境 | Python 3.11+，`uv` 管理 | 全面类型注解 |
| Web 框架 | FastAPI + Uvicorn | REST + SSE 流式 |
| LLM | OpenAI 兼容协议抽象 → DeepSeek / 豆包 / Qwen | 多 provider + fallback |
| Embedding | BGE-M3 / BGE-large-zh | 通过 provider 抽象 |
| Reranker | bge-reranker-v2（Cross-Encoder） | 精排 |
| 向量库 | Milvus（可插拔，兼容 Qdrant） | 抽象接口 |
| 全文检索 | Elasticsearch（BM25） | sparse 召回 |
| 缓存 | Redis | 精确 + 语义缓存 |
| 异步队列 | Celery + Redis | 文档入库流水线 |
| 文档解析 | MinerU / unstructured | PDF/布局/OCR |
| 可观测 | OpenTelemetry + Prometheus + Grafana + Langfuse | trace/metric/log |
| 评估 | RAGAS + 自研脚本 | 离线/在线 |
| 部署 | Docker + docker-compose（本地）/ k8s（生产） | CI/CD |
| 质量 | ruff + mypy(strict) + pre-commit + pytest | 覆盖率 |
