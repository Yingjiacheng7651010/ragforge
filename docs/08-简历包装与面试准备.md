### 项目标题
> **RAGForge —— 工程化企业级 RAG 平台（Python / FastAPI / Milvus / ES）**

### 一句话介绍（项目描述）
> 从零设计并实现了一个可评估、可观测、可降级的检索增强生成（RAG）系统，覆盖文档入库、混合检索、查询理解、生成与评估的完整链路，解决通用 RAG 检索精度低、幻觉高、无法量化优化的问题。

### Bullet Points（STAR + 量化，选 4~5 条）

```
• 【检索】实现多路召回（向量 Dense + BM25 Sparse）与 RRF 融合（k=60）+ Cross-Encoder 重排
  两级漏斗（召回 top-50 → 精排 top-8），支持 Milvus(HNSW/COSINE) 与 Elasticsearch
  (BM25 + dense kNN) 双后端，均已通过真实容器集成验证。

• 【查询理解】构建意图识别 + 查询改写 + 多查询扩展 + HyDE 的查询理解管线，prompt 全部外置
  （data/prompts/ 共 12 个模板）可调，多轮指代消解接入对话历史。

• 【抗幻觉】实现 Self-RAG/CRAG 检索自评纠错（sufficient/retry/insufficient，改写重试 ≤2 轮）+
  上下文 Token 预算（严格不超）+ 强制 [1][2] 引用溯源 + 输出护栏（LLM 语义判幻觉/不安全）。

• 【降本】设计精确(md5) + 语义(embedding 余弦, 阈值 0.92)双层缓存，命中即零 LLM 调用；
  文档更新按 doc_id 主动失效，敏感内容（邮箱/手机号/身份证）拒绝缓存。

• 【工程化】85 个源文件 / 4600+ 行、22 个包、18 次原子提交；全链路 OpenTelemetry（Jaeger 可见
  完整 span 树）+ Prometheus 指标 + structlog trace_id 关联；ruff/mypy(strict)/pytest CI 门禁——
  261 个测试、覆盖率 95.84%、核心模块(retrieval/generation/chunking/cache) 90%+。

  三工具 + 反思修正，最大步数/轮数硬上限防死循环）。
```

## 2. 面试必答 10 问（含参考思路）

### Q1：你的 RAG 和普通的有什么本质区别？
**思路**：不要只说"更复杂"，要说**三个可量化维度**——可评估（每个改动有指标）、可观测（全链路 trace）、可降级（fallback/熔断/缓存）。再补一句："我的核心逻辑是自研的，不依赖框架黑盒，所以每个环节都能解释为什么这么做。"

### Q2：为什么 Recall@5 有提升？具体做了什么？
**思路**：这是"展示评测闭环"的黄金问题。回答路径：先建黄金集（data/golden/qa.jsonl，人工标注 gold_chunks + 难度分层）→ 用 `python -m ragforge.eval run` 测基线 → 定位失败样例是"实体/编号类召回差" → 加 BM25 稀疏召回 + RRF 融合 → 再加重排 → 复测看 `--baseline` diff。**每个决策都对应一个失败 case 和一次指标变化**。当前 repo 示例黄金集可复现 `recall@5=0.67 / mrr=0.5`（含难度分层报告与 diff 对比），业务黄金集跑大后即可产出前后对比数字。

### Q3：混合检索里 RRF 怎么融合的？为什么不用加权分数？
**思路**：RRF 公式 `Σ 1/(k+rank)`，k=60。优点：不依赖各路的分数分布（dense 余弦相似度与 BM25 分数量纲不同，不可直接加权），只关心相对排名，稳定且无需调权。这是字节式"工程稳健性"思维。

### Q4：怎么降低幻觉（hallucination）？
**思路**：三层——① 检索层 Self-RAG 自评，资料不足时拒答而非硬答；② 生成层 Token 预算 + 强制引用，答案必须挂 [1][2]；③ 输出护栏用 LLM 校验答案是否可被上下文支撑（P13）。再用 faithfulness 指标量化。

### Q5：语义缓存怎么实现？会不会缓存到错误答案？
**思路**：query 转 embedding，Redis 里相似度 > 阈值(0.92) 命中。风险控制：① 阈值网格搜索权衡命中率与误命中；② 文档更新主动失效；③ 命中结果打标可审计；④ 命中返回时附 source_query 供追溯。

### Q6：父子分块（Parent-Child）解决什么问题？
**思路**：检索和生成对 chunk 长度的需求是**矛盾的**——小块检索精度高但语义破碎，大块语义完整但精度下降。父子分块用小块检索（child ~200 tokens）、大块生成（parent ~800 tokens），命中 child 后通过 parent_id 还原完整上下文，兼顾两者。

### Q7：LLM 挂了系统怎么办？
**思路**：provider fallback 链（`FallbackLLM`，按序尝试多个 provider）+ 幂等错误指数退避重试（`base·2^attempt`）+ 熔断半开（连续失败 5 次熔断 60s）+ 最终降级（语义缓存命中即返回，检索不足由 Self-RAG 明确拒答）。强调"绝不整链路雪崩"。

### Q8：你的评估指标怎么保证可信？不会"自己评自己"吗？
**思路**：① 黄金集核心部分人工标注，gold_chunks 人工确认；② LLM-as-judge 的裁判 prompt 独立于生成 prompt，且用人工标注样本校准 Judge 的准确率；③ 离线指标 + 线上 A/B 双验证，不只看离线。

### Q9：为什么要做 A/B 实验，离线好不就行了吗？
**思路**：离线指标衡量的是"在黄金集上"，与真实用户分布、真实延迟、真实反馈有偏差。在线 A/B 看的是真实用户点踩率、留存、成本。两者互补：离线快、可复现、成本低，用于快速迭代；在线用于最终决策。

### Q10：这个项目里你最有成就感的难点是什么？
**思路**：选一个**有具体数字的**，推荐"用 96% 覆盖率 + 261 个测试把每个模块行为锁死，且核心链路（Milvus/ES/Jaeger）真实集成验证通过"，或"语义缓存精确/语义双命中，命中即零 LLM 调用"。按 STAR：背景 → 问题 → 分析 → 行动 → 量化结果 → 反思。业务指标类数字（如 recall 对比、成本降幅）务必是跑出来的再讲。

## 3. 面试官可能的深挖（提前准备）

| 向量索引选型 | HNSW vs IVF 的权衡、ef/参数含义、召回率与 QPS 的 trade-off |

| 缓存一致性 | 文档更新 → 按 doc_id 清缓存；TTL 兜底 |
| 流式怎么做 | SSE，TTFT 作为指标 |
| 多租户/权限 | 检索时按 metadata 过滤，文档级权限隔离 |
