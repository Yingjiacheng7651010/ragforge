# 05 · 评估体系

> 字节式 RAG 的第一原则：**没有评估的优化都是玄学**。
> 本文档定义：测什么指标、用什么数据、怎么测（离线/在线）、怎么用结果驱动迭代。

---

## 1. 评估为什么是简历核心竞争力

面试官问"你怎么知道你的 RAG 变好了？"——
- 普通回答："感觉回答更准了。" ❌
- 优秀回答："我在黄金集上跑 recall@5 / faithfulness，改动前后对比，recall 从 0.81 提到 0.90，faithfulness 从 0.85 提到 0.92，且线上 A/B 显示用户点踩率下降 20%。" ✅

**本项目 = 评估驱动开发（Eval-Driven Development）**：每个设计决策（分块大小、重排开关、prompt 措辞）都用指标证明。

## 2. 指标体系（三层）

### 2.1 检索层指标（Retrieval）
| 指标 | 定义 | 目标 |
| --- | --- | --- |
| Recall@k | 前 k 个结果中命中正确答案的比例 | ≥ 0.90 (k=5) |
| Precision@k | 前 k 个结果中相关结果的比例 | 参考 |
| MRR | 正确答案排名的倒数均值 | ≥ 0.80 |
| Hit Rate | 至少命中一次的比例 | ≥ 0.95 |

### 2.2 生成层指标（Generation，RAGAS）
| 指标 | 定义 | 目标 |
| --- | --- | --- |
| Faithfulness | 答案是否忠于上下文（无幻觉） | ≥ 0.90 |
| Answer Relevance | 答案是否切题 | ≥ 0.85 |
| Context Relevance | 检索上下文是否相关 | ≥ 0.85 |

### 2.3 系统层指标（System，线上）
| 指标 | 定义 | 目标 |
| --- | --- | --- |
| Latency P50/P95/P99 | 端到端/各阶段耗时 | P95 ≤ 3s |
| TTFT | 首 token 延迟 | ≤ 1s |
| Cost per Query | 单次查询成本 | 记录并优化 |
| Cache Hit Rate | 缓存命中率 | ≥ 30% |
| 用户点踩率 | 线上反馈 | 越低越好 |
| Error Rate | 错误率 | ≤ 0.1% |

## 3. 黄金评测集（Golden Dataset）构建

**格式（JSONL）**：
```jsonl
{"id":"qa_001","question":"语义缓存默认阈值是多少？","gold_answer":"0.92","gold_chunks":["chunk_123"],"doc_id":"docs/cache.md"}
{"id":"qa_002","question":"如何为新员工开通权限？","gold_answer":"...","gold_chunks":["chunk_456"],"doc_id":"docs/admin.md"}
```

**构建流程**：
1. **人工标注核心集**：从真实文档里人工写 50~100 条 Q-A-证据chunk 三元组（质量最高，必须人工）。
2. **合成数据扩充**：用 LLM 基于文档段落生成 (question, answer) 对，再人工抽检。
   - 合成 prompt 要求：问题可回答、答案唯一、覆盖不同难度（单跳/多跳）。
3. **难度分层**：easy（单段直答）/ medium（多段综合）/ hard（多跳推理），分别看指标，定位短板。
4. **版本管理**：黄金集随文档库演进，纳入 git，标注 `golden/v1`。

> ⚠️ 黄金集是评测的"尺子"，尺子不准一切白搭。核心集必须人工，且要保证 `gold_chunks` 真的能回答问题。

## 4. 离线评估流程

```
1. 准备：加载黄金集 + 已入库的文档
2. 检索评估：对每个 question 跑检索，算 recall@k / MRR / hit rate
3. 生成评估：检索结果 → 生成答案 → RAGAS 算 faithfulness / relevance
4. 输出报告：总指标 + 按难度分层指标 + 失败样例明细
5. 对比：与上一版基线 diff，标出提升/回退
```

```bash
# 统一入口
python -m ragforge.eval run \
    --dataset data/golden/qa.jsonl \
    --retriever hybrid \
    --metrics recall@5,mrr,faithfulness,answer_relevance \
    --baseline report/latest.json
```

**报告产物**：
```json
{
  "retrieval": {"recall@5": 0.91, "mrr": 0.82, "hit_rate": 0.96},
  "generation": {"faithfulness": 0.92, "answer_relevance": 0.87},
  "by_difficulty": {"easy": {...}, "medium": {...}, "hard": {...}},
  "failed_cases": ["qa_007", "qa_033"]
}
```

## 5. 用评估驱动迭代（Eval Loop）

把每个可调项都当"超参"，跑评测选最优：

| 决策点 | 评估方式 |
| --- | --- |
| 分块大小/重叠 | recall@5 + faithfulness，扫参数网格 |
| 分块策略（结构 vs 语义） | 同数据集对比 recall |
| 是否开重排 | 开/关重排对比 recall@5、MRR |
| RRF 的 k 值 | 网格搜索 |
| 是否开多查询扩展 | 开/关对比 recall |
| prompt 措辞 | faithfulness + answer_relevance 对比 |
| 语义缓存阈值 | 命中率 vs 误命中率权衡 |

**原则**：**一次只改一个变量**，改完必出评测报告，报告附在 PR 里。

## 6. 在线评估（A/B 实验）

```
用户请求 → 实验分流层（按 user_id hash）
   ├── 对照组 A：当前线上版本
   └── 实验组 B：新版本（如新分块策略）
   → 采集：延迟、成本、缓存命中、用户赞踩、留存
   → 显著性检验 → 决策：全量 / 回滚
```

**实验平台要点**（简历可写）：
- 分流稳定（同用户始终同组）。
- 指标看板实时化（Grafana）。
- 灰度策略：5% → 20% → 50% → 100%，每步观察核心指标。
- 一键回滚：实验配置即代码，切换版本零代码改动。

## 7. 面试高频追问与应答要点

| 追问 | 应答要点 |
| --- | --- |
| 你的评估指标怎么来的？ | 三层指标（检索/生成/系统）+ 目标值，说明每个指标衡量什么 |
| 黄金集怎么保证质量？ | 核心集人工标注 + 合成扩充人工抽检 + 难度分层 |
| faithfulness 怎么算的？ | LLM-as-judge 把答案拆成原子陈述，逐条判断能否被上下文支撑 |
| 怎么防止"自己评自己"？ | 评测用独立裁判 prompt + 少量人工校准基线，Judge 本身也要被校准 |
| 离线好就一定线上好吗？ | 不一定，所以还要 A/B 在线验证，两者互补 |
| 语义缓存会不会缓存错误答案？ | 阈值调优 + 文档更新主动失效 + 缓存命中打标可审计 |
