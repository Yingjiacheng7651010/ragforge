# 01 · 系统架构设计

> 本文档定义 RAGForge 的**分层架构、技术选型理由、核心数据流与部署拓扑**。
> 设计原则：**接口先行、依赖注入、横向可插拔、纵向可观测**。

---

## 1. 分层架构总览

```
┌─────────────────────────────────────────────────────────────────┐
│  接入层  Access Layer                                            │
│  FastAPI (REST + SSE 流式) · 鉴权 · 限流 · 输入校验 · 统一响应     │
├─────────────────────────────────────────────────────────────────┤
│  编排层  Orchestration Layer                                     │
│  RAG Pipeline (DAG) · Agentic RAG (多跳/工具/反思) · 工作流引擎    │
├─────────────────────────────────────────────────────────────────┤
│  检索层  Retrieval Layer                                         │
│  查询理解(意图/改写/多查询/HyDE) · 多路召回 · RRF 融合 · 重排 · 自评 │
├─────────────────────────────────────────────────────────────────┤
│  生成层  Generation Layer                                        │
│  LLM Provider 抽象 · 流式/结构化输出 · 上下文装配 · 引用溯源        │
├─────────────────────────────────────────────────────────────────┤
│  数据层  Data Layer                                              │
│  文档解析 · 分块(结构/语义/父子) · Embedding · 向量库 · 文档库 · 缓存 │
├─────────────────────────────────────────────────────────────────┤
│  横切层  Cross-cutting Concerns                                  │
│  配置 · 日志 · Tracing · Metrics · 实验(A/B) · 评估 · 护栏/安全     │
└─────────────────────────────────────────────────────────────────┘
```

**关键设计决策：核心逻辑不绑定任何 LLM 框架。**
- 检索、重排、分块、上下文装配等核心算法**自研**，保证可控、可测、可优化。
- LangChain/LlamaIndex 仅作为**可选适配器**存在，不侵入核心。这体现的是"我理解原理，而不是只会调包"。

## 2. 核心数据流

### 2.1 离线入库（Ingestion）数据流

```
原始文档(PDF/Word/MD/网页)
   → [解析] 文本+版面结构+表格+图片(OCR)
   → [清洗] 去噪/去重/规范化
   → [分块] 结构感知分块 → 生成 小块(child) + 父块(parent) 元数据
   → [Embedding] 批量向量化(BGE-M3)
   → [入库] Dense 向量→Milvus；Sparse(BM25)索引→Elasticsearch；原文→文档库
   → [异步队列] Celery 任务，失败重试 + 死信队列 + 状态机
```

### 2.2 在线问答（Query）数据流

```
用户问题
   → [1 查询理解] 意图识别 → 查询改写 → 多查询扩展 → HyDE 假设文档
   → [2 多路召回] Dense(Milvus) + Sparse(ES/BM25) 并行召回 top-k
   → [3 融合] RRF 融合多路结果
   → [4 重排] Cross-Encoder 精排 → top-n
   → [5 自评] Self-RAG：检索相关性自评，不足则改写重试(CRAG)
   → [6 上下文装配] Token 预算 + 去重 + 父子块还原 + 引用标记
   → [7 生成] LLM 流式生成(带引用) + 输出护栏
   → [8 缓存回写] 语义缓存写入
   → [9 观测] 全程 trace/metric 上报 + 用户反馈采集
```

## 3. 技术选型与理由（面试必答）

| 组件 | 选型 | 为什么（字节式理由） |
| --- | --- | --- |
| 包管理 | `uv` | 极快、lock 文件可复现，避免 poetry/pip 的锁冲突 |
| Web | FastAPI | 原生 async、自动 OpenAPI、SSE 流式友好 |
| LLM 抽象 | OpenAI 兼容协议 | 一套接口接 DeepSeek/豆包/Qwen，多 provider 热切换与 fallback |
| Embedding | BGE-M3 | 中文强、支持 dense+sparse 双向量，开源可本地部署 |
| 重排 | bge-reranker-v2 | Cross-Encoder 精排，召回精度提升关键 |
| 向量库 | Milvus | 支持混合检索、亿级规模、索引可调（HNSW/IVF） |
| BM25 | Elasticsearch | 成熟、可扩展、支持字段过滤 |
| 缓存 | Redis | 低延迟、支持 TTL、可做语义缓存与限流 |
| 队列 | Celery + Redis | 入库是重任务，必须异步削峰 |
| 解析 | MinerU | 中文 PDF/版面/公式/表格解析 SOTA |
| 观测 | OpenTelemetry + Langfuse | 标准化 trace，LLM 调用可追踪 |
| 评估 | RAGAS + 自研 | 开源基线 + 自研指标补盲区 |

**选型心法（面试讲）**：所有外部依赖（LLM、向量库、embedding、reranker）都**抽象成接口**，通过配置切换。理由：模型和引擎会持续迭代，生产系统不能被某个具体产品锁死。

## 4. 接口抽象设计（依赖倒置）

```
ragforge/
├── core/
│   ├── llm/            # LLMProvider 抽象 (BaseLLM)
│   ├── embeddings/     # EmbeddingProvider 抽象
│   ├── reranker/       # Reranker 抽象
│   ├── vector_store/   # VectorStore 抽象
│   ├── retriever/      # Retriever 抽象
│   └── chunker/        # Chunker 抽象
```

每个抽象用 `Protocol` 定义（鸭子类型），具体实现放在 `providers/` 下，通过依赖注入容器装配。

```python
# core/vector_store/base.py —— 接口示例（面试可展示）
class VectorStore(Protocol):
    def add(self, chunks: list[Chunk]) -> None: ...
    def search(
        self, query_embedding: list[float], top_k: int, filters: dict | None = None
    ) -> list[SearchHit]: ...
    def delete(self, doc_id: str) -> None: ...
```

> 这样写的好处：换 Milvus → Qdrant 只改配置 + 一个新实现类，核心逻辑零改动。这就是**开闭原则（OCP）**的落地。

## 5. 部署拓扑

### 5.1 本地开发（docker-compose）

```
docker-compose.yml
├── api          # FastAPI 服务
├── worker       # Celery 入库 worker
├── milvus       # 向量库
├── etcd         # milvus 依赖
├── minio        # milvus 对象存储
├── elasticsearch
├── redis
├── prometheus   # 指标采集
├── grafana      # 面板
├── jaeger       # trace 展示
└── langfuse     # LLM 观测
```

### 5.2 生产（k8s 概念图，简历可提）

```
Ingress → API (多副本 HPA) → Milvus/ES/Redis (有状态，StatefulSet)
        ↘ Worker (按队列长度 HPA)
观测：DaemonSet(采集) → Prometheus → Grafana
发布：GitHub Actions → 镜像 → k8s 灰度(Canary) → 全量
```

## 6. 可靠性设计（字节式"别让它挂"）

| 机制 | 实现 |
| --- | --- |
| LLM fallback 链 | provider 按优先级链式调用，失败自动降级到下一个 |
| 重试 | 指数退避 + 抖动（retry with backoff+jitter） |
| 熔断 | 连续失败 N 次打开熔断器，半开探测 |
| 降级 | 语义缓存 miss 且 LLM 全挂 → 返回检索摘要（降级答案） |
| 限流 | API 层令牌桶，保护下游 |
| 超时 | 每层调用设 timeout，链路预算控制 |
| 幂等 | 入库任务幂等（doc_id 去重），重复投递安全 |
